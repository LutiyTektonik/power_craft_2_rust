# Инструкции для следующих задач

Рабочий репозиторий — этот каталог. Служебный `/workspace/.git` не является нашим репозиторием. Сохранять изменения пользователя; работать в отдельной ветке, без force push. Документация и отчёты — по-русски.

## Продолжение на локальном компьютере

Репозиторий: https://github.com/LutiyTektonik/power_craft_2_rust , исходная рабочая ветка `work/transport-detector`. Локальные изменения начинать отдельной веткой. Не создавать проект заново, не сбрасывать нумерацию 0.4.0. Пользовательская игровая база — `powercraft2-v0.2.0-tested`; detector/Speedy-разгрузка требуют отдельной игровой приёмки. Cloud-пути в старых документах не являются требованиями к локальному расположению.

На Windows 11 поддерживаемый сценарий скриптов — WSL2 Ubuntu 24.04, локальный Codex внутри WSL, проект в Linux-файловой системе. Это инструкция, а не подтверждение Windows-прогона. Требования: Bash, Git, Python >=3.11, curl, build-essential, rsync, pkg-config, libasound2-dev, libudev-dev; Rust 1.95.0/rustfmt/Clippy закреплены в rust-toolchain.toml. Установка системных пакетов и clone приведены в README.md. Затем `scripts/bootstrap.sh --install`, `source scripts/env.sh`, `scripts/check.sh`. В каждом новом терминале повторять source. Bootstrap может компилировать cargo-horizon-mod; для полной интеграции нужно не менее 6 ГиБ свободного диска перед стартом. Не переносить облачные кэши и авторизацию. Полные команды — docs/LOCAL_DEVELOPMENT.md.

Для резервного переноса из чистого коммита: `python3 scripts/export-local.py`. Bundle содержит историю/ветки/теги, source — только снимок файлов. Проверять восстановление через настоящий clone bundle и git fsck; не обещать Git-историю при Download ZIP. Установочные пакеты остаются вне Git, входят в переносной ZIP и должны совпадать с SHA-256 отчёта. Не менять игровой код в рамках переноса окружения.

## Архитектура и код

- Одна небольшая Cargo-библиотека, без сторонних зависимостей. `transport.rs` одновременно используется нативным модулем; не создавать вторую копию механики.
- Независимая механика не обращается к Horizon, часам, файловой системе или сети. Rust-код в `listen.rs`, `item_tick.rs`, `client_tick.rs`, `placement.rs` связывает её с движком.
- Модульные payload-файлы не должны содержать внутренних атрибутов, `//!`, внешних `mod` или `include!`: ограничения Mixins.
- Не добавлять пустые реализации будущих Core/Logic/Storage/Mobile. Расширять их после проверки Transport.
- Проверять конечность чисел и границы перед преобразованием координат. Не использовать `unwrap`/`expect` для данных мира. Ошибочные и устаревшие сущности пропускать.
- Состояние направления — штатное свойство блока `facing`. Не сохранять runtime-ID сущностей между событиями. Не создавать дублирующее хранилище чанков.

## Совместимость

- Только `powercraft2:*`, модуль `powercraft2_transport`; не писать в чужие namespaces.
- Использовать именованные хуки каталога с `hook_version`; не перехватывать внутренние функции ради удобства. Нет OVERWRITE и отмены чужих тиков.
- Нет обязательных других модов. Будущая совместимость — отдельные адаптеры.
- Пины обновлять согласованно в `upstream.lock.json`, `compatibility.json`, манифесте и доказательствах API. Не подставлять `main` вместо SHA.
- `native/tools/*.py` — точные внешние upstream-файлы в игнорируемом локальном каталоге. Не добавлять их в Git без подтверждения лицензии. Загрузка — `python3 scripts/fetch-tools.py --download`; обновлять ревизию и `TOOL_PROVENANCE.json` при обоснованном обновлении.
- Не заявлять общую совместимость и работоспособность без сборки/игровых проверок. См. `docs/COMPATIBILITY.md`.

## Проверки

```sh
scripts/check.sh --static
scripts/check.sh
scripts/build.sh --source-only
scripts/check.sh --horizon
```

Полная интеграция тяжёлая и требует сети, Rust и rsync; не повторять её бесконечно при нехватке ресурсов. При исправлении 0.1.1 Rust 1.95.0, rustfmt, Clippy и rsync установлены локально в `.tools/`. Для использования выполнить `source scripts/env.sh`. Для 0.4.0 реально прошли 45 Rust- и 28 Python-тестов; прежний отчёт о недоступности компилятора — история первоначального прототипа. Официальную проверку и игровые прогоны различать по текущему `docs/VERIFICATION.json`.

Ревизия Windows 11: `docs/WINDOWS11.md`, `docs/FEATURE_AUDIT.md`, `docs/WINDOWS11_VERIFICATION.json`. После упаковки `python3 scripts/prepare-windows.py` создаёт тестовый набор. `native-pinned/` в нём убирает только необязательное `hooks`, чтобы Launcher не сменил Horizon SHA; обе ревизии и Rust-payload должны сохраниться. Текущие Python-проверки — 28 тестов. Официальная интеграция и валидаторы прошли для 0.4.0; три ленты 0.2.0 подтверждены пользователем, передача требует игрового прогона.

Все сборки/источники сторонних проектов держать в игнорируемых каталогах. Не добавлять игровые ресурсы, секреты, `target`, Cargo-кэш и полные исходники Horizon в Git. Не менять прокси, TLS или ограничения среды ради скачивания. Никаких внешних сообщений без указания пользователя.

Версия 0.1.1 исправляет server/client prediction. Цель — фактический Horizon пользователя 9f42064c11efe7ef3e5ed2baad7ddc2a3b36eea0, Mixins e59da9094f0c2fdda6c627fe9eff22dec6a906f0. Событие tick после клиентской физики использует ту же velocity_for_tick, что server Post. В клиентском адаптере допускается только запись velocity собственного ItemEntity: публичный setter запрещает client writes. Не писать position/previous, stack/age/pickup_delay, не отправлять свои position packets. Это pin-specific мост, не стабильный API; документирован в SMOOTH_MOVEMENT.md. Контент остаётся 0.1.0, native — 0.1.1. Официальный native.py сначала упаковывает источники, затем `prepare-windows.py --native-only` убирает только необязательный hooks и делает строгий распространяемый pin. Проверять именно файл из dist валидатором Horizon.

## Продолжение 0.2.0

Проверенная база: тег powercraft2-v0.1.1-tested, BASELINE.md/BASELINE_DATA.json. Не менять старый ID, facing, форму и восемь закреплённых normal-файлов. Для выпуска с новым контентом версии синхронны; filenames в scripts вычисляются из manifest, без возврата к фиксированному 0.1.0.

Клиент читает это свойство, не серверный helper (он возвращает 0 на клиенте). Кэш обновляется при обработке предмета; не обещать мгновенный индикатор пустой ленты. Не добавлять полный скан чанков или свои position packets.

Поддерживать PORTING_PROGRESS.md, ORIGINAL_REGISTRY.md, ARCHITECTURE.md, COMPATIBILITY.md, TESTING.md, VERIFICATION.json и CHANGELOG.md. Категории незавершённого оригинала не смешивать со статусом порта. Полный индекс оригинала — ORIGINAL_MECHANICS.json; воспроизведение inventory-original.py --source с обязательной проверкой всех blob ID. Java-тексты/графику не добавлять в Git.

Первый срез vanilla-передачи выполнен в 0.3.0; после его приёмки — детекторная лента и оставшийся рабочий Transport. Никакая отсутствующая реализация сама по себе не доказывает блокировку API. Для игры 0.2.0 обновляются обе части; rollback мира только из копии до новых блоков.

## Актуальные дополнения 0.3.1/0.4.0

Пользователь прямо разрешил Speedy-разгрузку и продолжение прогресса. Это отменяет прежнее ограничение 0.3.0; не удалять разгрузку. Сохранять targets/грани/64-лимит/скорость. Детектор как новый вид не разгружается: исключение не переносится на будущие Belt автоматически.

Не писать position/стек/игрока при детектировании. Сигнал из state-only, 15/0 strong/weak, source только свой, neighbor notify на переходах и первом загруженном тике.

После reload перепроверить занятость/оповестить сеть; выключенный на сервере мод очищает питание, не опрашивая сущности. Не обещать отсутствие тиковых затрат: BE tick движка помечает chunk dirty, поршни этот блок не двигают, массовая нагрузка не измерена.

Для ru/en и creative tab приложены исходные JSON, тест разрешает только добавление без потери старых ключей/элементов. Не менять существующие рецепты/ID/facing/форму/скорости. ## Продолжение 0.5.0

Локальная ветка `work/transport-redirector` от `dd34b14`. На 0.4.0 в Windows подтверждены три пустых сундука, частичный и нулевой приём Speedy, а также сигнал детектора с игроком и предметом. Сохранение при повторном входе и LAN остаются отдельными сценариями.

Redirector следует опубликованной 0.1.0B с учётом координатных таблиц `PC_Direction`: под питанием предпочитает правый по ходу доступный бок, затем левый. При выключении и двух боковых лентах без ленты сзади поворачивает налево. Разгрузка использует поставленный facing; движение и предсказание используют общий вычисленный маршрут. Не сохранять runtime ID и не менять пины. Следующая механика после приёмки 0.5.0 — сортирующая лента.
