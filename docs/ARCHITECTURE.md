# Архитектура PowerCraft 2 Horizon

Одна Cargo-библиотека содержит чистое Transport-ядро `transport.rs`. Этот же файл официальный Mixins добавляет как `powercraft2_transport` в staged Game. Нет дублирования механики и сторонних Cargo-зависимостей. Core/Logic/Storage/Mobile — будущие логические области, без пустых пакетов.

## Границы и поток данных

1. `content/` регистрирует три собственных блока с предметами, facing, формой, ресурсами, loot и рецептами. Powered есть только у нового `brake_conveyor`; данные старого `conveyor` не изменены.
2. `placement.rs` узнаёт только свои Belt::from_block ID, выбирает facing по yaw и сохраняет уже данный другим обработчиком ответ.
3. `listen.rs` включает серверный Post, не сбрасывая чужое listened.
4. `item_tick.rs` читает временный typed EntityRef/LevelRef только для minecraft:item. Для Brake читает `Host::neighbor_signal`, при изменении записывает только собственный powered через `set_block_property_with(..., 2)`. Обычная/быстрая ленты не читают питание и не пишут блоки.
5. Чистая `belt_velocity_for_tick` выбирает вариант: Normal вызывает прежний `velocity_for_tick` без изменений; Speedy использует ×2; Brake без питания ×0,6, с питанием только гасит X/Z на ×0,6. Общая проверка контакта, конечности чисел и сохранение Y обязательны.
6. Адаптер проверяет следующий загруженный блок и задаёт скорость серверной сущности. Движение/коллизии/сохранение выполняет Horizon.
7. `client_tick.rs` работает только на remote-копии после физики через официальный tick. Он читает то же состояние блока, включая опубликованный powered, и вызывает то же ядро. Минимальный pin-specific мост меняет только ItemEntity::velocity; позиции/previous/стек/возраст/подбор не меняет.

## Тики и питание

Скорости задаются в блоках на игровой тик: 0,1 / 0,2 / 0,06. Это не часы реального времени и не FPS. Текущий порт сохраняет проверенную модель ограниченной скорости; старое накопление boost/max-speed не возвращается. Сохраняются характерные отношения параметров оригинала, а не его побитовая траектория или высота 1/16.

Публичный native_neighbor_signal возвращает 0 на клиенте. Поэтому клиенту нельзя самостоятельно читать его и считать питание отсутствующим. Powered публикуется сервером стандартным block-state update только при изменении, без собственных пакетов и без UPDATE_NEIGHBORS. Передача не добавляет постоянных position packets и не создаёт рекурсии redstone.

Powered — кэш последнего измерения при контакте/обработке предмета. Без предметов состояние/картинка могут оставаться прежними до следующего контакта; это явно ограничение первого среза тормозной ленты. При появлении нового предмета сервер заново читает реальный сигнал, включая после загрузки чанка. Начальное значение false не является разрешением доверять сохранённому питанию на сервере. Обычная задержка доставки изменения клиенту возможна и требует игровой проверки переключения. Нет глобального списка лент или фонового сканирования мира.

## Данные и сохранение

Существующий `powercraft2:conveyor` и facing=north|east|south|west сохранены. Восемь исходных файлов normal-контента побайтно совпадают с проверенной базой; `BASELINE_DATA.json` закрепляет их hashes. Новые ID не переиспользуют старые состояния. Speedy хранит facing; Brake — facing и boolean powered в штатном block state Horizon. Отдельной block entity/NBT-схемы для этих лент нет.

Сущности, предметные компоненты, возраст, слияние, despawn и pickup принадлежат движку. Runtime-ID не сохраняется. Незагруженный следующий чанк тормозит X/Z; нормальная политика entity-ticking chunks остаётся у Horizon. Повреждённые направления, нечисловые координаты, отсутствующий/устаревший handle приводят к пропуску воздействия.

Для следующих инвентарей/фильтров/таймеров потребуются версионированные данные, лимиты и атомарные операции. Не переносить Forge NBT/metadata или PC_WorldData как совместимый формат без мигратора.

## Производительность и дальнейшее развитие

Чистое ядро O(1), без выделений. Клиентский проход O(видимые предметы), без копирования списка. Typed server helpers могут искать сущность линейно; Brake дополнительно запрашивает шесть соседних сигналов на обрабатываемый предмет и меняет свой state лишь по необходимости. Профилирование большой нагрузки ещё не проводилось; не заявлять O(1) всему игровому модулю.

Первый срез передачи в vanilla-инвентари реализован в 0.3.0; следующий компонент — детекторная лента. Фильтры/GUI использовать отдельно от движения, транзакции размещать только на сервере. Общая регистрация, конфигурация и сериализация должны расширяться ровно по необходимости, без собственной замены игрового движка или Java API.

## Серверная передача 0.3.0

После общей проверки контакта и до записи прежней скорости сервер вызывает чистый storage_targets и ограниченный Transfer. Снимок исходного ItemStack берётся через Host::item_entities только при допустимой соседней цели. insert_item меняет контейнер по штатным правилам, затем set_item_entity записывает точный остаток/удаляет источник. Клиентский адаптер 0.2.0 и placement не менялись. Поддержанные типы ограничены проверенным синхронным путём; новый глобальный реестр/таймер/схема сохранения не создаются. Детали гарантий и оставшегося объёма — STORAGE_TRANSFER.md.

Текущий охват переноса изменён: экспериментальные Logic/Storage/Mobile и неисправные/незавершённые подфункции отложены. Расширяются только существующие рабочие механики, с сохранением принятых адаптаций. Опубликованный реестр отделён от GitHub-снимка; при расхождении факты релиза не подменяются поздним исходником.
