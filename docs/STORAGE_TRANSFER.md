# Передача предметов в инвентарь: 0.3.0

Восстановлена часть storeNearby опубликованного PowerCraft 2 0.1.0B: обычная и тормозная ленты передают выброшенные предметы в соседние контейнеры. Новых блоков, предметов, рецептов и GUI нет. Все 29 файлов content/assets и content/data версии 0.2.0 побайтно сохранены; меняется только версия content manifest для согласованной установки.

## Поведение по оригиналу

- Normal начинает передачу после достижения половины блока по facing, включая точный центр.
- Brake без питания использует ту же границу, с питанием — игнорирует границу половины, оставаясь в пределах штатной проверки контакта.
- Приоритет: впереди по facing; затем два поперечных соседа в исходном порядке north/east/south/west; затем сверху. Сзади и снизу передачи нет.
- Полный контейнер возвращает всё, частичное принятие оставляет остаток, затем проверяется следующая цель. Полное принятие удаляет исходную item entity.
- Speedy в опубликованном PCtr_BlockBeltSpeedy не вызывает storeNearby. Его не расширяем: завершайте быструю линию обычной лентой перед контейнером.

Условия контакта, скорость и клиентское предсказание из проверенной 0.2.0 не переписаны. Передача не работает для летящих мимо предметов и не загружает чанки.

## Реальные API и учёт количества

Серверный entity_tick_post проверяет мод, сущность, уровень, свой блок, facing, on_ground и конечность чисел. Чистый storage_targets выдаёт до четырёх целей с настоящей принимающей гранью (для контейнера сверху — Down). Проверяются loaded и имя целевого блока.

Поддержаны семь проверенных обычных типов: minecraft:chest, trapped_chest, furnace, hopper, dispenser, dropper, brewing_stand. Двойной сундук обрабатывается штатным view Horizon. Типы имеют реализации в проверенном движке, но все семь игровых сценариев Cloud не запускал.

Host::item_entities (API 42) даёт временный снимок точной исходной сущности по ID, только при наличии допустимой цели. Host::insert_item (API 20) сохраняет правила сторон, слотов, полного сравнения компонентов и максимальных размеров стека Horizon. Не переписываем слоты сами. После принятия Host::set_item_entity (API 42) задаёт точный остаток, при нуле удаляет сущность штатным путём. Копируются все компоненты ItemStack; меняется только count. Возраст, owner, задержка подбора и движение не пересоздаются.

У всей операции общий лимит **64 предмета на сущность за тик**, а не на каждую цель. Обычный классический стек переносится целиком, искусственно увеличенный — за несколько тиков. Это ограничение работы API insert_item, который вставляет по одному; повреждённый count=u32::MAX не создаёт бесконечного цикла. Transfer проверяет returned<=offered, не использует saturating arithmetic для скрытия ошибочного ответа и сохраняет равенство исходное количество = принятое + остаток.

## Граница атомарности

Это последовательное игровое действие под единственным &mut Game, без await, файлового I/O или переключения мира между вставкой и записью остатка. В выбранных обычных контейнерах insert_stack_through → move_in_item → view_changed не вызывает обработчик с изменяемым Game, который мог бы удалить исходный предмет. Политика native_container_accepts для ModContainer принимает только &Game, но произвольные контейнеры здесь всё равно не включены. Источники machines.rs, machines/native_items.rs и native_hooks.rs проверены по удалённым Git blob ID.

Контейнеры с дополнительными эффектами, например composter/jukebox/shelf, и чужие mod-контейнеры **не включены**: нельзя обещать им те же гарантии без анализа callbacks/транзакционного API. Это не универсальная транзакция для любого мода и не гарантия crash-atomicity при аварийном завершении процесса. Не расширять whitelist по одному лишь наличию slots.

При невозможном для проверенного контракта oversized remainder или исчезновении source после вставки записывается ошибка и повторных попыток в этом обработчике нет. Это сигнал нарушения engine/API-контракта; произвольного отката чужого инвентаря мод не делает. Обычные устаревшие Post/сущности отбрасываются до вставки. Контракт нужно заново проверить при любом изменении Horizon.

## Сохранение и сеть

Horizon помечает изменённые контейнеры/чанки и обновляет меню/компараторы. Источник и его исчезновение синхронизирует штатный tracker; свои пакеты и клиентские записи стека не добавляются. При частичной передаче видимое количество обновится по обычным правилам tracker. Передача выполняется только сервером; одновременные pickup/действия игроков проходят через обычный порядок тика Horizon.

У мода нет нового долгосрочного состояния, списка лент или незавершённых транзакций для выгруженного чанка. Новые требования к миру/схемам и миграция не добавлены. Реальное сохранение и LAN требуют игровой приёмки.

## Проверки и ограничения

37 Rust-тестов включают приоритет/грани всех направлений, границу половины, powered Brake, отсутствие Speedy-передачи, отрицательные координаты, фильтр поддержанных типов и количественный учёт. Перебор 0..255 предметов и разных вместимостей проверяет conservation/лимит; это модель ответов API, не запуск настоящих сундуков/печей. Прежние 25 тестов движения продолжают проходить.

Официальный native.py check применил Mixins и скомпилировал типы настоящего Horizon с модом. Валидация архивов прошла; внутри игры 0.3.0 ещё не запускался. Вагонетки, новые/mod-контейнеры, особая упаковка, bucket/bottle-действия, оригинальная despawn-политика и прочий Transport остаются вне этого среза.

Стоимость пути включает до четырёх чтений соседей, снимок item_entities только возле допустимых целей и до 64 insert attempts. Typed helpers могут искать сущность линейно; массовая нагрузка ещё не профилирована. Не обещать постоянную стоимость всему адаптеру.
